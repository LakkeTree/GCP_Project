# 최종 제품 요구사항 문서 (PRD)

모바일 게임 결제 혜택 통합 비교 및 최적 결제 경로 추천 서비스
문서 버전: v1.0 (Final) | 작성일: 2026-08-19
기준 문서: 1차 PRD, 2차 PRD(v0.1~v0.3), 2차 SRS(v0.2), 2차 문제정의서(v0.2), 최종 문제정의서(v1.0), GCP_Project 저장소 코드 감사(2026-08-19)

**개정 노트 (v0.3 → v1.0)**: 2차 PRD가 코드 감사로 남긴 "부분구현/미구현" 표시 항목 중 이번 발표 전 반드시 마무리해야 하는 항목을 FR-16~FR-19로 신규 편성했다. 유저 정보 저장소가 PostgreSQL(Cloud SQL)로 전환되고 관리자 대시보드(유저 모니터링)가 구현된 사실을 반영했다. KPI는 실제로 계측 가능한 지표만 남기고 나머지는 명시적으로 보류(3차 이후)로 재분류했다. 문제정의서와의 역할 중복은 최종 문제정의서 0장에서 확정한 원칙(문제정의서=배경/비전, 본 PRD=요구사항/KPI)에 따라 해소했다.

## 1. 요약

**제품 정의**: 모바일 게임 결제 결정을 지원하는 플랫폼·게임사·결제수단·멤버십·상품권 혜택 통합 분석 서비스. 중복 적용 가능한 조합을 계산하고 실질 결제비용 기준 최적 결제 경로(적용 순서 및 아웃링크)를 추천한다.

**최종 라운드 범위**: 계산 로직의 검증 가능성 확보, 관리자용 유저·데이터 모니터링, 게임 목록 자동화 파이프라인, Cloud Run 실배포 4개 축을 완료하여 "발표 가능한 완성형 프로토타입"으로 마무리한다.

**핵심 성공 지표**:
* `POST /routes` 계산 결과가 회귀 테스트 시나리오와 100% 일치
* 관리자 대시보드에서 유저 지표 + 데이터(크롤링) 신선도를 모두 확인 가능
* 게임 목록이 결제수단과 동일 수준으로 BigQuery 자동 반영
* 고정 Cloud Run URL로 외부에서 접속 가능하며 배포 전 보안 블로커 0건

## 2. 배경 정보

### 2.1 1차·2차 프로토타입 성과 요약

* 1차: 단일 게임(쿠키런: 킹덤) 기준 정적 데이터 기반 최적가 계산·정렬 로직의 정확성(100%)을 QA 단계에서 검증.
* 2차: FastAPI(`game-pay-api`) + React(`fe-app`) + BigQuery(5개 도메인 21개 스크레이퍼) 구조로 실제 애플리케이션화. Google OAuth 로그인, Dual-Track 추천(모달 비교), TOP 50 게임 목록 확장, 게임 추가 요청/아웃바운드 클릭 로그 백엔드가 구현되었으나 프론트엔드 연동, 로컬 저장 동의 UI, 자동 크롤링 스케줄링, 배포는 미완이었음.

### 2.2 최종 라운드 착수 시점의 현황 (코드 감사 기준)

| 영역 | 상태 |
| :---- | :---- |
| 사용자 저장소 | **PostgreSQL(Cloud SQL) 전환 완료**(`database.py`), SQLite 폴백 제거 |
| 관리자 대시보드(유저) | **구현 완료**(`GET /admin/stats/summary`, `GET /admin/users`, `AdminDashboardPage.tsx`, `require_admin` 권한 검사) |
| 관리자 대시보드(데이터) | 미구현 — 화면·API 모두 없음 |
| 계산 엔진 | 로직은 성숙(스태킹 레이어·상품권 우회 등 반영 이력 있음)하나 자동 검증 테스트 없음, `route_id` 미발급 |
| 게임 목록 파이프라인 | 순위 수집·정규화·매트릭스 생성은 자동화, BigQuery 반영은 수동(CSV 저장까지만) |
| 배포 | Dockerfile은 준비되었으나 Cloud Run 배포 파이프라인·실제 URL 없음 |
| 보안 | CORS 와일드카드+자격증명 병행, 개발용 인증 우회 경로(`DEBUG=True`), 서버 예외 원문 노출, Rate Limiting 부재 — 모두 미해결 |

이 표가 최종 라운드에서 처리해야 할 작업의 출발점이다.

## 3. 문제 정의 및 개선 과정

1차/2차에서 정의된 6개 문제(①사용자 데이터 비지속성 ②통합/플랫폼별 기준 모호성 ③대상 게임 부족 ④체리피킹 실사용 증거 부족 ⑤데이터 파이프라인 부재 ⑥표준 UI 미확립)의 상세 서술과 해결 과정은 2차 PRD 3장을 그대로 준용하며, 최종 상태는 최종 문제정의서 2장 표를 따른다. 본 장에서는 최종 라운드에서 신규로 편성된 4개 문제만 상술한다.

### [문제 7] 계산 로직의 실효성 미검증

**현상(As-Is)**: `engine/calculator.py`는 STORE_COUPON → PAYMENT_PG/PAYMENT_E_PAY → CARD_ISSUER 4계층 스태킹, 상품권 우회 등 실데이터를 반영해온 이력이 파일 상단에 남아 있어 로직 자체의 완성도는 높다. 그러나 이를 자동으로 검증하는 테스트가 전혀 없고, `recommend_best_routes()`가 반환하는 route 객체에 고유 식별자(`route_id`)가 없어 사용자가 실제로 그 경로를 선택해 결제로 이어갔는지 추적할 방법이 없다.

**상세 및 한계**: "계산이 맞다"는 것과 "그 계산대로 결제할 때 실제로 그 혜택이 적용된다"는 것은 다른 차원의 검증이다. 현재는 전자조차 자동화되어 있지 않고, 후자는 API 계약 결함(route_id 부재)으로 측정 인프라 자체가 없다.

**최종 라운드 해결 과제 (To-Be)**:
* 대조 시나리오(결제금액×보유 결제수단 조합) 10~20건에 대한 회귀 테스트 스위트 구축, 사람이 수기로 계산한 값과 100% 일치 검증
* `POST /routes` 응답에 `route_id` 필드 추가
* `POST /events/outbound-click` 프론트엔드 연동 완료로 "추천 → 클릭 → 외부 결제 페이지 이동"까지 실제 동작 확인
* 대표 시나리오 1건 이상 수동 E2E(실제 스토어/카드사 페이지까지 이동하여 표시된 할인율이 계산값과 일치하는지) 확인

### [문제 8] 운영 모니터링 체계 부재

**현상(As-Is)**: 서비스가 실제 사용자에게 노출되기 시작하면 "몇 명이 쓰고 있는가"뿐 아니라 "혜택 데이터가 최신 상태인가"를 상시 확인할 수 있어야 하나, 후자를 확인할 수단이 없었다.

**상세 및 한계**: 관리자 대시보드의 유저 모니터링(가입자·DAU/WAU/MAU·활성 유저 목록)은 이미 구현되어 있다. 그러나 크롤링이 성공했는지, 마지막으로 언제 데이터가 갱신되었는지, 어느 도메인이 실패했는지를 보여주는 화면·API·로그 테이블이 전혀 없다. 이 상태에서는 혜택 데이터가 오래되어도 아무도 알아채지 못한다.

**최종 라운드 해결 과제 (To-Be)**:
* `crawl_status_log` 테이블 신설 (도메인, 실행 시각, 성공/실패, 수집 건수, 실패 사유)
* `GET /admin/data-status` API 및 관리자 대시보드 내 "데이터 모니터링" 탭 신설
* 24시간 이상 갱신되지 않은 도메인에 대한 경고 배지 표시

### [문제 9] 게임 목록 관리의 확장성 한계

**현상(As-Is)**: 결제수단 혜택 크롤러(`card_data`, `store_data`, `epay_data`, `voucher_data`, `telecom_data`)는 GCS 업로드 → Cloud Function → BigQuery 자동 반영까지 완결된 파이프라인을 갖췄다. 반면 게임 목록 파이프라인(`game-benefit-pipeline/catalog`)은 순위 수집(`rankings.py`) → 정규화(`normalize.py`) → 호환성 매핑(`compatibility.py`) → 매트릭스 생성(`build_game_matrix.py`)까지는 자동화되어 있으나, 그 결과를 BigQuery `game_info`에 반영하는 것은 수동이다.

**상세 및 한계**: `rankings.py`는 자체 주석으로 "실제 라이브 사이트로 최종 검증되지 않았다"고 명시하고 있으며, 갤럭시스토어 컬럼은 항상 공란, 원스토어는 robots.txt 차단으로 제외되어 있다. 결제수단과 동일한 신뢰 수준에 아직 도달하지 못했다.

**최종 라운드 해결 과제 (To-Be)**:
* `build_game_matrix.py` 출력 결과를 결제수단 파이프라인과 동일한 방식(BigQuery MERGE 업서트)으로 반영하는 단계 추가
* 신뢰 불가 컬럼(갤럭시스토어 등)은 결과에 `false`/`null`로 명확히 표기하고 UI에서 "정보 미확인"으로 구분 노출
* `mobile_game_data/`와의 파이프라인 중복은 문서로 정리(§10 제약사항 참조), 실제 통합은 3차 과제로 이관

### [문제 10] 프로덕션 미배포로 인한 실사용 검증 불가

**현상(As-Is)**: `game-pay-api/Dockerfile`은 `$PORT` 환경변수를 사용하는 gunicorn+uvicorn 구성으로 Cloud Run 배포에 즉시 사용할 수 있는 형태이나, 실제로는 로컬 `uvicorn --reload`와 `npm run dev`로만 구동되어 왔다. 프론트엔드의 `API_BASE`도 `http://127.0.0.1:8000`으로 하드코딩되어 있다.

**상세 및 한계**: 발표 시연이 개발자 로컬 환경에 의존하는 것은 신뢰도와 재현성 면에서 리스크가 크다. 또한 외부에서 접근 가능한 URL이 없다면 아웃바운드 클릭·게임 요청 등 실사용자 행동을 관찰할 방법도 없다.

**최종 라운드 해결 과제 (To-Be)**:
* `game-pay-api`를 Cloud Run 서비스로 배포, 고정 URL 확보
* `fe-app`을 정적 호스팅(Cloud Storage + Cloud CDN 또는 Cloud Run 정적 서빙) 또는 Cloud Run 컨테이너로 배포하고 `API_BASE`를 배포 URL로 전환(빌드 시 환경변수 주입)
* §8 비기능요구사항의 배포 전 보안 체크리스트 통과를 배포의 선행 조건으로 명시

## 4. 목표

**단기(발표 전) 목표**: FR-16~FR-19 4개 과제를 완료하고, 그 결과로 얻어진 고정 URL 기준으로 전체 사용자 플로우(검색→조건→결과→클릭)와 관리자 플로우(로그인→유저 현황→데이터 현황)가 한 번의 시연으로 오류 없이 재현되는 것을 확인한다.

**중장기 목표**: 2차 PRD에서 정의한 확장 로드맵(TOP 50 이상 게임 확대, 결제수단 범위 확장, 자동 스케줄링, 유료 BM 적용)을 유지하되, 이번 라운드는 "새 기능"이 아니라 "이미 만든 것의 신뢰성·가시성·접근성 확보"에 전념한다.

## 5. 사용자 / 시나리오

Primary/Secondary/Tertiary 타겟 정의는 1차 PRD를 그대로 유지한다(최종 문제정의서 4장 참조). 최종 라운드에서 관리자 페르소나를 공식 추가한다.

**시나리오 C (문제 7·10 관련)**: 개발팀 PM이 발표 리허설 중 관리자 계정으로 Cloud Run 배포 URL에 접속해, 최근 1시간 내 3명의 신규 유저가 `POST /routes`를 호출했고 이 중 1명이 실제로 [구매하기] 링크를 클릭해 스토어 페이지로 이동한 것을 관리자 대시보드에서 확인한다. 동시에 "데이터 모니터링" 탭에서 카드사 크롤러가 6시간 전에 마지막으로 성공했음을 확인하고 안심한다.

**시나리오 D (문제 9 관련)**: 게임 목록 담당 개발자가 `game-benefit-pipeline`을 실행하면, 신규 인기 게임이 자동으로 BigQuery `game_info`에 반영되어 별도의 수동 CSV 업로드 없이 검색 결과에 즉시 노출된다.

## 6. 요구사항 (FR)

1차 PRD의 FR-1~FR-8, 2차 PRD의 FR-9~FR-15는 그대로 유지하되, 코드 감사에 따른 최신 상태를 아래와 같이 갱신한다. FR-16~FR-19는 최종 라운드 신규 요구사항이다.

### 6.1 기존 FR 상태 갱신 (2차 대비 변경분만 기재)

| FR | 2차 상태 | **최종 상태** |
| :-- | :---- | :---- |
| FR-9 (로컬 저장) | 부분구현, Opt-in UI 없음 | 변화 없음 — **최종 라운드 필수 완료 대상**(AC-9.1) |
| FR-10 (계정 기반 저장) | 구현됨(SQLite 기반) | **PostgreSQL(Cloud SQL) 기반으로 전환 완료**. 개발용 인증 우회 코드는 `DEBUG` 플래그로 가드되었으나 **배포 시 반드시 `False` 필요**(§8) |
| FR-11 (Dual-Track) | 부분구현(모달 대체 UI) | **모달 비교 UI를 정식 사양으로 확정**(AC-11.1/11.2 갱신) |
| FR-12 (게임 확장/추가 요청) | 백엔드만 구현 | **최종 라운드 필수 완료** — 프론트 연동(요청 버튼 → API 호출) |
| FR-13 (아웃바운드 클릭 트래킹) | 백엔드만 구현, API 계약도 미완성(route_id 없음) | **최종 라운드 필수 완료** — FR-16과 함께 route_id 발급 후 프론트 연동 |
| FR-14 (자동 크롤러) | 결제수단 5도메인 구현, 자동 스케줄링 없음 | 결제수단은 유지. **게임 목록도 FR-18로 자동화 수준 격상**. 스케줄링(Cloud Scheduler)은 3차 과제로 재확인 |
| FR-15 (표준 UI) | 구현됨 | 변화 없음. 관리자 대시보드가 4번째 표준 페이지 그룹으로 추가됨(FR-17) |

### 6.2 FR-16. 계산 로직 신뢰성 검증 및 결과 추적 (문제 7)

`POST /routes`가 반환하는 각 경로에 고유 `route_id`를 발급하고, 사전 정의된 대조 시나리오 집합에 대해 계산 결과가 결정론적으로 일치함을 자동 테스트로 검증한다. 계산 결과와 실제 클릭 행동을 `route_id`로 연결하여 추적 가능하게 한다.

### 6.3 FR-17. 관리자 대시보드 — 데이터 모니터링 (문제 8)

관리자가 로그인 후, 유저 현황(기구현)에 더해 도메인별(카드/스토어/이페이/상품권/통신사/게임) 최근 크롤링 성공 여부, 마지막 수집 시각, 수집 건수를 한 화면에서 확인할 수 있다. 24시간 이상 미갱신 도메인은 경고로 강조 표시한다.

### 6.4 FR-18. 게임 목록 자동 수집·반영 파이프라인 (문제 9)

게임 순위·플랫폼 호환성 수집 결과를 결제수단과 동일한 방식으로 BigQuery `game_info`에 자동 업서트한다. 신뢰도가 낮은 필드(예: 미검증 스토어 지원 여부)는 별도 플래그로 구분해 저장한다.

### 6.5 FR-19. 프로덕션 배포 (Cloud Run) (문제 10)

`game-pay-api`와 `fe-app`을 각각 배포하여 고정 웹 URL로 서비스에 접근할 수 있도록 한다. 배포는 §8에 정의된 보안 체크리스트를 모두 통과한 이후에만 수행한다.

## 7. 인수 기준 (AC)

FR-9~FR-15는 2차 PRD의 AC-9.x~AC-15.x를 유지하되, 다음 항목을 갱신·추가한다.

* **AC-9.1 (갱신)**: 최초 결과 화면 진입 시 로컬 저장 Opt-in 배너가 노출되고, 동의 시에만 Local Storage에 저장한다. 미동의 시 세션 메모리만 사용한다.
* **AC-11.1 (갱신)**: 결과 화면은 "전체 통합 최적가" 카드를 기본 노출하고, 사용자가 특정 플랫폼을 선택하면 모달로 해당 플랫폼 한정 최적 조합을 비교 표시한다(탭 UI 아님).
* **AC-12.4 (갱신, 기존 v0.2 조건부 → 최종 확정)**: "게임 추가 요청" 버튼 클릭이 실제로 `POST /games/request` 호출까지 이어지는 End-to-End 동작이 QA 통과 조건이다.
* **AC-13.4 (갱신)**: `[구매하기]` 클릭이 실제로 `POST /events/outbound-click` 호출까지 이어지며, 이때 `route_id`가 함께 전달되어야 한다.

**FR-16 AC**
* AC-16.1 `POST /routes` 응답의 모든 route 객체는 서로 중복되지 않는 `route_id`를 포함해야 한다.
* AC-16.2 사전 정의된 10~20개 대조 시나리오에 대해 자동 테스트 실행 시 계산 결과가 사람이 계산한 기준값과 100% 일치해야 한다.
* AC-16.3 대표 시나리오 1건 이상에 대해 실제 외부 결제 페이지까지 수동으로 이동하여 표시된 할인 조건이 추천 결과와 일치함을 QA 체크리스트로 기록해야 한다.

**FR-17 AC**
* AC-17.1 관리자 대시보드에 "데이터 모니터링" 탭이 추가되어야 하며, 도메인별 최근 크롤링 시각·성공 여부·수집 건수가 표시되어야 한다.
* AC-17.2 24시간 이상 갱신되지 않은 도메인은 시각적으로(배지/색상) 구분되어야 한다.
* AC-17.3 관리자가 아닌 사용자는 해당 화면·API에 접근할 수 없어야 한다(기존 `require_admin` 재사용).

**FR-18 AC**
* AC-18.1 `game-benefit-pipeline` 실행 완료 후 별도의 수동 업로드 없이 BigQuery `game_info`에 신규/변경 게임이 반영되어야 한다.
* AC-18.2 신뢰도가 검증되지 않은 필드는 API 응답에서 `null` 또는 별도 플래그로 구분되어야 하며, 프론트는 이를 "정보 미확인"으로 표시해야 한다.

**FR-19 AC**
* AC-19.1 배포된 Cloud Run URL로 외부 네트워크에서 전체 사용자 플로우(검색→조건→결과→클릭)가 오류 없이 동작해야 한다.
* AC-19.2 배포 시점에 CORS 허용 출처가 배포 프론트엔드 도메인으로 명시적으로 제한되어야 한다.
* AC-19.3 배포 환경의 `DEBUG` 값이 `False`여야 하며, 개발용 인증 우회 경로가 실제로 차단됨을 테스트로 확인해야 한다.
* AC-19.4 서버 예외 발생 시 클라이언트에는 일반화된 메시지만 반환되어야 한다(원문은 서버 로그로만).

## 8. 비기능 요구사항 (변경·신규 항목)

### §8-A. 배포 전 필수 보안 조치 (P0, Go-Live Blocker)

2차 SRS(NFR-11~14)가 지적한 항목이 최종 라운드 착수 시점까지 미해결로 남아있음을 코드 감사로 재확인했다. 이 4개 항목은 기능 완성도와 별개로 **Cloud Run 배포를 막는 게이트**로 취급한다.

| 항목 | 현재 상태 | 조치 |
| :-- | :---- | :---- |
| CORS | `allow_origins=["*"]` + `allow_credentials=True` 동시 사용 | 배포 도메인만 명시적 허용 리스트로 전환 |
| 인증 우회 | `.env`의 `DEBUG=True`로 인해 `usr_` 접두 토큰이 서명 검증 없이 통과 | 배포 환경변수에서 `DEBUG=False` 강제, 우회 코드는 해당 조건에서만 비활성화됨을 테스트로 확인 |
| 예외 노출 | 다수 엔드포인트가 DB/BigQuery 예외 원문을 그대로 반환 | 클라이언트 응답 일반화 + 서버 로그 상세 기록으로 분리 |
| Rate Limiting | 전무 | 미인증 엔드포인트에 최소 호출 빈도 제한 도입 |

### §8-B. 성능

`POST /routes` 응답 P95 3초 이내 목표는 1차부터 유지. 관리자 대시보드 API(`/admin/*`)는 실시간성이 낮으므로 별도 SLA를 두지 않되, 5초 이내 응답을 권장 기준으로 한다.

### §8-C. 데이터 정합성

게임 목록 자동 업서트(FR-18) 도입에 따라, `benefit_info`와 동일하게 신뢰도 검증이 안 된 레코드를 구분하는 원칙(2차 PRD의 `review_status` 개념)을 `game_info`에도 적용할지는 3차 과제로 남긴다(§ 향후 과제).

## 10. 제약 / 의존성 / 리스크 (갱신)

* **파이프라인 중복**: `mobile_game_data/`와 `game-benefit-pipeline/catalog/`가 유사 목적으로 공존한다. 최종 라운드는 후자를 공식 파이프라인으로 채택하고, 전자는 문서상 폐기 예정(deprecated)으로 표기하되 코드 삭제는 3차 과제로 이관한다.
* **환경설정 리스크**: 코드는 개발용 인증 우회를 `DEBUG` 플래그로 가드하도록 개선되었으나, 실제 배포 시 환경변수 값이 잘못 설정되면(예: `.env`를 그대로 복사) 즉시 보안 사고로 이어진다. 배포 체크리스트에 환경변수 값 확인을 명시적 단계로 둔다.
* **SQLite 잔재**: `game-pay-api/game_pay.db`는 더 이상 참조되지 않으나 저장소에 남아있어 향후 혼란 소지가 있다. 정리 대상으로 기록만 하고 이번 라운드 필수 항목에서는 제외한다.
* **게임 데이터 신뢰도**: FR-18로 자동화 수준을 높이더라도 갤럭시스토어 등 일부 데이터는 여전히 미검증 상태로 남는다. 이를 사용자에게 숨기지 않고 명시하는 것으로 리스크를 관리한다(AC-18.2).

## 11. 릴리스 및 롤아웃 계획

1. **1단계 — 신뢰성 확보**: FR-16(계산 검증), FR-12/13 프론트 연동을 우선 완료한다. route_id가 나머지 작업의 선행 조건이므로 최우선 배치.
2. **2단계 — 관측 가능성 확보**: FR-17(데이터 모니터링), FR-18(게임 파이프라인 자동화) 병행 진행.
3. **3단계 — 보안 하드닝**: §8-A 4개 항목 조치.
4. **4단계 — 배포**: Cloud Run으로 `game-pay-api` 배포 → 프론트엔드 `API_BASE`를 배포 URL로 전환 후 `fe-app` 배포 → 3단계 체크리스트 재확인 → 외부 접속 스모크 테스트.
5. **5단계 — 문서화 및 발표 준비**: 본 PRD/SRS/문제정의서 최종본 확정 → 발표 자료 제작.

**롤백 계획**: Cloud Run은 리비전 기반 배포이므로, 문제 발생 시 이전 정상 리비전으로 트래픽을 즉시 되돌린다. 데이터베이스는 Cloud SQL 자동 백업을 활용하며, 스키마 변경(`crawl_status_log` 추가 등)은 롤백 가능한 마이그레이션 스크립트로 관리한다.

## 15. 리스크

1차·2차 리스크 목록(성능, 보안, 중복 규칙 모델링, 접근성)은 유지한다. 최종 라운드 신규 리스크는 다음과 같다.

* **배포 직후 실사용 트래픽에 의한 미발견 버그 노출 리스크** → 완화: 배포 전 §11 4단계 스모크 테스트, 문제 발생 시 즉시 이전 리비전 롤백
* **보안 조치 누락 상태로 배포될 리스크(환경변수 오설정)** → 완화: 배포 스크립트에 환경변수 검증 단계 포함, 배포 담당자 체크리스트 서명 절차
* **발표 시연 중 실시간 크롤링/외부 사이트 의존 데이터의 변동성** → 완화: 시연 직전 데이터 스냅샷 확보, 데이터 모니터링 화면으로 최신성 사전 확인

## 16. 고객지지(장애 대응) 계획

배포 이후 실제 사용자가 유입될 수 있으므로, 서비스 장애·오류 발생 시 대응 절차를 최소한으로 정의한다.
* 관리자 대시보드의 데이터 모니터링(FR-17)을 1차 장애 감지 수단으로 사용한다.
* 서버 로그(Cloud Run 로그, `crawl_status_log`)를 1차 조사 자료로 사용한다.
* 발표 기간 중에는 개발팀이 직접 모니터링하며, 별도 CS 채널은 이번 라운드 범위 밖이다.

## 18. 오픈 이슈 최종 결정 기록

2차 PRD 18장에 남아있던 질문들을 아래와 같이 최종 확정한다.

* **로컬 저장 Opt-in 배너 UX**: 최초 결과 화면 하단 배너, "저장" 선택 시에만 Local Storage 사용(AC-9.1).
* **계정 시스템 우선순위**: 이미 FR-10이 먼저 완성되어 논의 종료(2차 문서 확인 사항 유지).
* **TOP 50 선정 기준**: 연간 매출액 기준으로 통일(최종 문제정의서 §9).
* **크롤링 대상 우선순위**: 5개 도메인 모두 구현 완료로 해결.
* **아웃바운드 클릭 식별자 필요성**: **필요함으로 확정** — 익명 세션 단위 집계(route_id + 클릭 시각)로 충분, 개인 식별자는 여전히 미사용.
* **Dual-Track 재설계 여부**: 재설계하지 않음, 모달 UI 확정(§7).
* **크롤러 스케줄링 방식(Cloud Scheduler vs GitHub Actions)**: 3차 과제로 유예, 이번 라운드는 자동 업서트까지만.
* **관리자 인증 체계**: `role` 컬럼 확장 방식으로 확정, 이미 구현됨.
* **CORS/인증 우회 코드 제거 시점**: 배포 직전 게이트로 확정(§8-A).
* **CTR 계측을 위한 impression_log 도입 여부**: 이번 라운드 보류, 클릭 수 집계로 대체(§17).
* **문제정의서 3장 vs 본 PRD 12/17장 KPI 중복**: 최종 문제정의서 0장에서 확정한 원칙에 따라 본 PRD가 KPI를 전담하고 문제정의서는 이를 참조만 한다.
