## 0. 이 문서의 성격과 최종본 작성 배경

1차·2차 프로토타입 단계에서는 문제정의서(3장 문제 정의, 12장 KPI)와 PRD(3장 문제 정의, 12장 KPI) 사이에 서술이 미세하게 어긋나는 문제가 반복적으로 발생했다(예: TOP 50 게임 선정 기준이 두 문서에서 "게임 다운즈 기준"과 "연간 매출액 기준"으로 다르게 적혀 공식 문서끼리 충돌). 2차 문서들은 이 문제를 "PRD가 최신 기준"이라는 원칙으로 임시 봉합하고, 향후 두 문서 중 하나를 흡수 통합할 것을 스톱이슈로 남겼다.

**최종본에서는 이 스톱이슈를 다음과 같이 확정한다.**

* 본 문제정의서는 **왜(Why) 이 서비스를 만드는가** — 시장 배경, 문제 정의, 차별화, 비즈니스 모델, 장기 비전 — 을 다루는 상위 기획 문서로 역할을 한정한다.
* **무엇을(What) 만드는가**의 기능 상세(FR/AC)와 KPI 측정 방법론은 전량 PRD로 위임하며, 본 문서는 KPI를 직접 나열하지 않고 PRD 17장을 참조한다.
* **어떻게(How) 만드는가**의 기술 상세는 전량 SRS로 위임한다.
* 세 문서가 상충하는 내용을 담을 경우 **PRD → SRS → 본 문서** 순으로 우선한다.

이 원칙에 따라 본 문서는 1차/2차 문제정의서 대비 분량을 줄이고, 배경·차별화·BM·비전 서술에 집중한다.

## 1. 프로젝트 배경

### 1.1 시장 구조: 모바일 게임 결제 시장의 성장과 집중

* 2025년 전 세계 모바일 게임 매출은 상위 100개 게임에 약 57%(약 466억 달러)가 집중되어 있으며, 2026년에는 58%(약 530억 달러)까지 확대될 전망이다(Sensor Tower, *State of Gaming Report*).
* 국내 모바일 게임 매출 비중은 전체 게임 시장의 약 60%를 차지하며, 상위 100개 게임의 83%가 5~7종의 결제·수익화 메커니즘(패키지, 시즌패스, 배틀패스, 뽑기 등)을 동시 운영한다.
* 신규 콘텐츠 출시·이벤트 시점의 매출은 평시 대비 300~1,000% 급증하는 등, 결제 수요의 시간적 집중도가 매우 높다.

### 1.2 사용자 측 문제: 파편화된 혜택 정보와 계산 피로

* 국내 모바일 게임 인앱결제 이용자의 70% 이상이 2030 핵심 과금층에 집중되어 있으며, 이들은 신규 콘텐츠·이벤트 결제 시 최소 5개 이상의 채널(플랫폼 자체 할인, 게임사 웹샵 이벤트, 카드사 청구할인, 간편결제 이벤트, 통신사 멤버십, 상품권 환전)을 직접 순회 확인해야 최적가를 찾을 수 있다.
* 혜택마다 최소 결제금액, 할인 한도, 중복 적용 가능 여부 조건이 제각각이며, 이용자는 커뮤니티(뽐뿌, 디시인사이드, 네이버 게임 라이지 등)에서 수기로 정리된 "혜택 조합 가이드"에 의존하고 있다.

## 2. 문제 정의 및 최종 해결 현황

1차 프로토타입은 문제 1개(단일 게임·정적 데이터 기반 계산 로직 검증)를, 2차 프로토타입은 이로부터 파생된 6개 문제(①사용자 데이터 비지속성 ②플랫폼별 vs 통합 최적가 기준 모호성 ③대상 게임 부족 ④체리피킹 실사용 증거 부족 ⑤데이터 수집 파이프라인 부재 ⑥페이지별 UI/UX 미확립)를 다루었다. 코드 감사 결과, 이 중 다수가 해결되었고, 발표를 앞둔 최종 라운드에서 사용자가 직접 지목한 4개의 신규 문제가 추가되었다.

| # | 문제 | 1차 상태 | 2차 상태 | **최종 상태(2026-08-19 코드 기준)** |
| :-- | :---- | :---- | :---- | :---- |
| ① | 사용자 데이터 비지속성(재입력 피로) | 미해결 | 로컬 저장 부분구현 | 로컬 저장 부분구현 유지, **Opt-in 동의 UI 미구현** (배포 전 최종 마무리 대상) |
| ② | 통합 최적가 vs 플랫폼별 최적가 기준 모호 | 미해결 | Dual-Track 부분구현(모달 대체 UI) | **모달 비교 UI로 최종 확정**(탭 구조로의 재설계는 하지 않음) |

| ⑥ | 페이지별 표준 UI/UX 미확립 | 대상 외 | 3단계 표준 페이지 구현 완료 | **해결됨** |

### 신규 문제 (최종 라운드, 사용자 지목 4건)

| # | 문제 | 현황 | 최종 라운드 대응 |
| :-- | :---- | :---- | :---- |
| ⑦ | 계산 로직의 실효성 미검증 | `engine/calculator.py`는 스태킹 레이어·상품권 우회 등 실데이터 반영 이력이 있으나, 자동화된 검증 테스트가 전무하고 `route_id` 부재로 "추천 → 실제 결제 적용" 흐름 자체가 끊겨 있음 | 계산 로직 회귀 테스트 세트 구축 + `route_id` 발급으로 결과 추적 가능화 |
| ⑧ | 운영 모니터링 체계 부재 | 유저 모니터링(가입자/DAU/MAU, 관리자 대시보드)은 구현 완료. **데이터 모니터링**(크롤링 성공/실패, 데이터 신선도)은 화면·API 모두 없음 | 크롤링 로그 테이블 + 데이터 모니터링 화면 신규 구축 |
| ⑨ | 게임 목록 관리의 확장성 한계 | 결제수단은 크롤러→BigQuery 자동 업서트가 완성되어 있으나, 게임 목록(`game-benefit-pipeline/catalog/`)은 순위 수집~정규화까지만 자동화되고 BigQuery 반영은 수동 | 결제수단 파이프라인과 동일한 자동 업서트 단계로 확장 |
| ⑩ | 실배포 부재로 인한 실사용 검증 불가 | Dockerfile은 Cloud Run 배포에 즉시 쓸 수 있는 형태로 준비되어 있으나, 실제 배포 파이프라인·URL이 없어 로컬 환경에서만 동작 | Cloud Run 배포로 고정 웹 URL 확보 |

**아울러, 코드 감사 과정에서 2차 SRS가 지적했던 보안·안정성 결함 중 다음 항목들이 여전히 미해결 상태로 확인되어, 실제 웹 배포에 앞서 반드시 처리해야 하는 항목으로 격상한다.**

* CORS `allow_origins=["*"]` + `allow_credentials=True` 동시 사용(main.py)
* 개발용 인증 우회 경로가 `.env`의 `DEBUG=True` 설정 하에서는 여전히 활성 상태
* 서버 예외 원문이 클라이언트에 그대로 노출되는 다수의 엔드포인트
* Rate Limiting 미구현

자세한 내용과 조치 계획은 PRD 8장·SRS 6장을 참조한다.

## 3. 구현 방식 개요 (최종 아키텍처)

```
[5개 도메인 크롤러]                    [게임 목록 파이프라인]
card / store / epay / voucher /        game-benefit-pipeline/catalog
telecom_data (21개 스크레이퍼)          (순위수집→정규화→호환성매핑)
        │  BigQuery 자동 업서트                │  ※ 최종 라운드: BigQuery 자동 업서트로 격차 해소
        ▼                                      ▼
              BigQuery (asia-northeast3)
    benefit_info · platform_connection · game_info
    ( + 신규: crawl_status_log 크롤링 이력 )
                        │  읽기 전용
                        ▼
        game-pay-api (FastAPI, Cloud Run)
   engine/calculator.py : 혜택 필터링·중복 적용·경로 계산
   auth.py               : Google OAuth 검증 + 관리자 권한
   database.py (PostgreSQL / Cloud SQL) : users, 로그 테이블群
                        │
                        ▼
        fe-app (React + TypeScript, 정적 호스팅 또는 Cloud Run)
   일반 사용자 플로우(검색→조건→결과) + 관리자 대시보드(/admin)
```

1차 프로토타입 대비 달라진 핵심은 (1) 저장소가 계정 기반 PostgreSQL(Cloud SQL)로 전환되었고, (2) 유저 활동 로그와 관리자 대시보드가 추가되었으며, (3) 게임 목록도 결제수단과 동일한 원칙(자동 수집 파이프라인 + 정기 반영)으로 관리하는 것을 목표로 한다는 점이다. 최종 라운드는 이 아키텍처를 실제로 인터넷에 상시 노출된 Cloud Run URL로 배포하는 것을 완료 조건으로 삼는다.

## 4. 타겟 사용자 세그먼트

1차·2차와 동일하게 3-Tier 타겟 모델을 유지한다. 최종 라운드에서 관리자 대시보드가 구현됨에 따라 내부 운영자 페르소나를 공식 4번째 세그먼트로 추가한다.

| 세그먼트 | 정의 | 서비스 내 역할 |
| :---- | :---- | :---- |
| Primary: 스마트 체리피커 | 월 평균 10만 원 이상 결제, 2030 핵심 과금 유저 | 핵심 수익 창출층, 혜택 조합 가이드 자발적 확산 |
| Secondary: 고효율 추구 소과금러 | 월 1~5만 원, 1020 청년·청소년 | MAU·트래픽 기반층, 디스플레이 광고 잠재 인벤토리 |
| Tertiary: 편의 중심 무관심 과금러 | 결제 여력은 충분하나 정보 탐색에 무관심한 3050 직장인 | 향후 신규 유입 확장 대상 |
| **신규: 서비스 운영자(관리자)** | 유저 활동·데이터 신선도를 모니터링하는 내부 담당자 | `/admin` 대시보드를 통해 가입자·DAU/WAU/MAU, 크롤링 상태를 확인 |

## 5. 미션·핵심가치·비즈니스 모델 (요약)

1차·2차 문서에서 정의한 미션과 3대 핵심가치, Opening/Middle/Long Phase BM, 3단계 장기 확장 전략(모바일→PC/콘솔→전(全) 라이프스타일 결제 다비게이터)은 최종본에서도 그대로 유지한다. 프로토타입 단계의 목표는 이 비전을 향한 **핵심 계산 로직의 신뢰성**과 **실제 서비스로서 접근 가능한 형태**를 증명하는 것이며, BM/장기 비전에 대한 상세 서술은 1차 문제정의서 7~9장을 준용한다.

> **미션**: "지금 바로, 가장 합리적이고, 100% 안전한 최적의 결제 경험을 제공한다."

## 6. 최종 릴리스 범위 정의 (Definition of Done)

발표를 앞둔 이번 라운드는 신규 기능 확장이 아니라 **"만든 것이 실제로 동작하고, 검증 가능하고, 인터넷에서 접근 가능한 상태"**를 만드는 데 초점을 둔다. 상세 요구사항은 PRD FR-16~FR-21, SRS SR-18~SR-21을 따르며, 완료 기준은 다음 6가지로 요약한다.

| # | 항목 | 완료 기준 |
| :-- | :---- | :---- |
| 1 | 계산 로직 검증 | 대조 시나리오 기반 회귀 테스트 통과 + `POST /routes` 응답에 `route_id` 포함 + 클릭 추적 연동으로 "추천→실결제 경로 이동"까지 1회 이상 End-to-End 확인 |
| 2 | 관리자 모니터링 페이지 | 유저 모니터링(기구현) + **데이터 모니터링**(크롤링 성공/실패, 최근 수집 시각, 도메인별 데이터 건수) 화면 신규 추가 |
| 3 | 게임 목록 자동화 파이프라인 | `game-benefit-pipeline/catalog`가 결제수단 크롤러와 동일하게 BigQuery `game_info`를 자동 업서트 |
| 4 | 유저 정보 PostgreSQL | 이미 완료(Cloud SQL 연결 확인). SQLite 잔재 파일(`game_pay.db`) 정리만 남음 |
| 5 | 로그 테이블 | 유저 로그(`UserGameActivityLogModel`)는 기구현. **크롤링 로그 테이블**(`crawl_status_log`) 신규 구현 |
| 6 | Cloud Run 배포 | 고정 웹 URL로 프론트·백엔드 접속 가능, §7의 배포 전 필수 보안 조치 선행 |

이 6개 항목이 모두 완료된 이후에만 문서화(PRD/SRS 확정판 배포)와 발표 자료 준비 단계로 진입한다.

## 7. 배포 전 필수 조치 (Go-Live Blocker)

Cloud Run으로 실제 공개 URL을 발급하는 순간 이 서비스는 "로컬에서만 접근 가능한 프로토타입"에서 "누구나 접근 가능한 공개 웹 서비스"로 성격이 바뀐다. 코드 감사 결과 다음 4개 항목은 **기능 완성도와 무관하게 배포 이전에 반드시 조치**해야 하는 보안 결함이다. (상세 근거: SRS 6.2절)

1. **CORS 설정 수정**: `allow_origins=["*"]`와 `allow_credentials=True`를 동시에 쓰는 현재 설정은 자격증명 포함 요청을 사실상 모든 출처에 허용하는 결과를 낳는다. 배포 프론트엔드 도메인만 명시적으로 허용해야 한다.
2. **인증 우회 경로 비활성화**: `.env`의 `DEBUG=True`를 배포 환경에서는 `False`로 강제해야 한다. 현재 값 그대로 배포하면 `usr_`로 시작하는 토큰으로 Google 서명 검증 없이 임의 계정에 접근할 수 있다.
3. **서버 예외 메시지 마스킹**: 다수의 엔드포인트가 DB·BigQuery 예외 원문을 클라이언트에 그대로 반환한다. 사용자에게는 일반화된 메시지만, 상세는 서버 로그로만 남겨야 한다.
4. **Rate Limiting 도입**: 미인증 API(`/games/request`, `/games/search-log` 등)에 대한 최소한의 호출 빈도 제한이 없어 악용 시 로그 테이블 오염 위험이 있다.

## 8. 향후 과제 (발표 이후 3차 로드맵)

* Cloud Scheduler 등을 통한 크롤링 파이프라인의 완전 자동(정기) 트리거화 — 이번 라운드는 "자동 업서트"까지이며 "정기 자동 실행"은 범위 밖
* `mobile_game_data/`와 `game-benefit-pipeline/catalog/`로 이원화된 게임 데이터 파이프라인 통합
* CTR(노출 대비 클릭률) 측정을 위한 `impression_log` 도입 — 이번 라운드는 클릭 수 집계까지만 포함
* WCAG 2.1 AA 수준 접근성 고도화
* PC/콘솔 결제 플랫폼으로 계산 엔진 확장
* 유료 결제/구독 BM 적용
