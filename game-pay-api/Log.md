# 보안 관련 주의할점
데이터 저장 정책(Opt-in 기반)
1. 로컬 저장소(Local Storage) 및 개인정보(PII) 관리
    동의 기반 저장(Opt-in) 필수: 비회원 유저의 입력 정보를 브라우저 Local Storage에 저장할 때는 반드시 유저의 명시적 '저장하기' 동의(Opt-in)를 얻어야 합니다
                            미동의 시에는 기존 원칙대로 세션 종료 시 즉시 폐기해야 합니다
    개인식별정보(PII) 저장 금지 : 카드번호, 계좌번호 등 개인식별정보(PII)는 절대 수집 및 저장해서는 안 됩니다. 
                                저장 항목은 카드사명, 결제 수단 종류, 통신사 등 비식별 정보로 엄격히 제한해야 합니다
    유저의 데이터 제어권 보장: 유저가 저장된 정보를 언제든지 수정하거나 삭제할 수 있도록 '저장된 정보 삭제' 버튼을 제공해야 하며, 삭제 클릭 시 Local Storage 데이터가 즉시 삭제되어야 합니다.
2. 계정 기반 인증(OAuth) 및 회원 데이터 보안
    최소 권한 요청: 소셜 로그인(Google 등) 연동 시 이메일 및 식별자 등 최소한의 필수 권한만 요구해야 합니다
    비밀번호 자체 저장 금지: 계정 시스템 연동 시 표준 OAuth 라이브러리를 활용하고, 서비스 자체 DB에 비밀번호를 직접 저장 및 관리하지 않는 구조를 유지해야 합니다
    회원 탈퇴 시 즉시 파기: 유저가 회원 탈퇴를 요청할 경우 서버 DB에 적재된 '내 보유 혜택 자산' 프로필 데이터는 지체 없이 즉시 삭제되어야 합니다.
3. 크롤링 파이프라인 도입에 따른 법적·약관 준수
    공식 API 우선 및 법무 검토: 스토어 혜택 수집 시 법적·약관 위반 리스크를 최소화하기 위해 공식 API를 우선적으로 활용해야 합니다
        API 미제공 시에만 보완적으로 크롤링을 진행하며, 사전 법무 검토를 거쳐야 합니다
    robots.txt 및 이용약관 확인: 수집 대상 페이지의 robots.txt 설정과 이용약관을 미리 확인하고 준수해야 합니다
    트래픽 부하 방지(Rate Limiting): 대상 서버에 과도한 부하를 주지 않도록 크롤링 요청 간격(Rate Limiting) 및 주기(예: 1일 1회 이상)를 적절히 설정해야 합니다.
4. 로그 DB 적재 및 유저 데이터 익명화
    로그 익명성 유지: 게임 추가 요청(game_request_log) 및 저장 동의 여부(storage_opt_in_log) 등 데이터 분석용 로그를 DB에 적재할 때는 유저 개인을 식별할 수 없는 익명 레코드로 관리해야 합니다
    클릭 트래킹 시 개인정보 최소화: 아웃바운드 결제 링크 클릭률(CTR) 집계 시에도 비인증 세션 노출이나 개인정보 유출이 없도록 최소한의 비식별 식별자만을 활용하여 보안 리스크를 방지해야 합니다


1단계: 백엔드 API 검증 강화 및 로컬 데이터 규격 정의 (main.py 수정)
    1단계의 목적은 유저가 브라우저의 개발자 도구(F12)로 결제 금액을 마이너스(-50,000원)로 고치거나 알 수 없는 수단을 강제로 넣어 보낼 때, 서버가 터지지 않고 입구에서 안전하게 차단(Validation)하도록 만드는 것입니다
바뀐 점 : 1. platform: str -> platform: SupportedPlatform   바꾼 이유 :platform 칸에 "이상한스토어"라고 적어 보내도 백엔드가 아무 검사 없이 계산 엔진으로 넘겨서 오류를 발생시켰습니다
         2. amount: int   -> amount: int = Field(..., gt=0, le=10_000_000)   바꾼 이유: amount에 -50000(마이너스 5만 원)을 입력해도 계산 엔진으로 그대로 전달되어 할인 금액 연산 로직이 엉켰습니다.
         3. payment_methods: List[str] -> VALID_PAYMENT_METHODS 화이트리스트 + @field_validator   바꾼 이유: 유저가 ["KB_CARD", "<script>alert('해킹')</script>"] 같은 악의적인 문자열을 넣어 보낼 수 있었습니다
         4. try - except 예외 처리 블록 추가  추가 이유 : 계산 엔진 실행 중 예상치 못한 에러가 나도 서버가 다운되지 않고 안전하게 에러 메시지 반환.  

1단계 main.py 수정에 대한  프론트엔드 전달 사항 프론트엔드(웹/앱) 개발자가 확인/수정해야 할 3가지
      1. 결제 예정 금액(amount) 0원 이하 전송 금지 현상: 유저가 금액을 입력하지 않았거나 0원, 음수(-10,000원)를 입력한 상태로 추천 버튼을 누르면 백엔드에서 422 Unprocessable Entity 에러를 반환합니다
          프론트엔드 조치: 버튼 클릭 전 금액 필드가 0원 초과인지 프론트엔드 1차 유효성 검사(Validation)를 거치도록 구현합니다
      2.  플랫폼(platform) 및 결제 수단 코드 대문자 통일 :현상: 백엔드 화이트리스트는 GOOGLE_PLAY, KB_CARD, KAKAO_PAY 등 대문자 코드 기준입니다
          프론트엔드 조치: 백엔드로 POST /routes 요청을 보낼 때 소문자가 아닌 정해진 대문자 규격 코드로 전송하도록 맞춥니다[cite: 6]. (참고: main.py에 소문자를 대문자로 자동으로 바꿔주는 보완 로직을 넣어두었으나, 규격을 통일하는 것이 가장 안전합니다
      3.  Local Storage 보안 정책 적용 : 
          유저의 '저장 동의(Opt-in)' 체크박스 동의 시에만 브라우저 Local Storage에 저장
          카드번호, CVC 등 개인식별정보(PII)는 절대 저장하지 않고, 카드사 코드명만 저장
          저장된 정보 삭제' 버튼 클릭 시 localStorage.clear() 실행.

# 운영 DB / 
실시간 유저 회원가입 / 로그인 정보 , 빠른 조희 및 업데이트가 필요한 데이터

user_id: 우리 서비스 내부에서 사용하는 고유 식별자 (PK)

email / nickname: 사용자 프로필 정보

provider: 소셜 로그인 종류 (GOOGLE, KAKAO, NAVER)

provider_id: 구글/카카오에서 넘겨주는 핵심 고유 ID (소셜 로그인 시 이미 가입된 유저인지 판별할 때 기준이 됨)

role: 사용자 권한 (ROLE_USER = 일반유저, ROLE_ADMIN = 관리자)

is_first_pay / membership_tier: 작성하신 FastAPI 결제 추천 엔진(RouteRequest)에서 유연하게 연동해서 쓸 수 있는 사용자 상태 값
